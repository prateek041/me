In the modern days, if we are building a coding harness that gives the AI agents their true potential, we would have to give them their own computers to work with. This sounds like a comparatively easy problem and something that a lot of companies are already working on. The problem space is called **Agent Sandboxing**.

There are so many companies already involved in it, in-fact, the moment when this article is being written, it is the hottest space in the entire AI surface. Agents are getting deeper and deeper into the system, even [reaching operating systems](https://openai.com/index/introducing-shirudo/).

The philosophy is quite simple, the agents can write more configurations of any command ever run in the CLI, they can write better bash scripts, they are so smart now that they explore the system itself before making decisions, re-check their work and fix it on their own if it breaks. This directly means that we should hand-off the terminal to them now, the question is where does that terminal run?

Is that terminal directly accessing your personal hardware? your laptop? or is it a cloud machine? There are different restraints with different configurations really. Running cloud machines is renting hardware, and you pay for every minute you run it. It also takes away the ownership of things, there is only so much you could do with a generalized public solution, because the person renting the thing to you did not build it just for you, they built it for being used for everyone, and in case you want a custom solution, you have to pay a custom price.

The other way is your personal laptop, but as you can think now, it is not safe. LLMs can be re-routed from their own goal and even be hijacked. So we either reduce the security surface of running things on our own laptops, or we re-strict the agents and their capabilities. We cannot do the second option anymore and the first option is not any good either.

That is where [karya](https://www.usekarya.dev/) comes into the picture.

## System Syncing in Karya

We have two different systems, one is the host and the other is the sandbox, and there are two actors overall, one in each system, which can make changes to the system content independently. There are the following constraints in the systems.
- Host can only be changed by the user through the following methods:
  - Manually editing things.
  - Accepting a path/diff/change coming from the sandbox. (Actual application logic is written in the harness)
  - The final liability is on the human who is accepting changes into the Host system.
- Sandbox can only be changed the following way:
  - The agent running things in the sandbox.
  - The user that might have changed somthing in the host.

This sandbox and everything inside it, we are going to call it the workspace, and everything in it is now going to be formalized through a workspace interface that works on top of the sandbox interface.

```go title="Karya's Sandbox Interface"
// Sandbox is an isolated VM that works as a personal computer for an
// AI agent.
type Sandbox interface {
	// Start creates and runs a microVM sandbox and return's it [Executor] interface
	// back to the caller.
	Start(ctx context.Context, name string) (Executor, error)
	// Stop halts and gracefully shuts down the sandbox.
	Stop(context.Context) error
	// Remove destroys the sandbox and clears the resources.
	Remove(context.Context) error
}
```
The sandbox interface is right now used a life-cycle management interface for a sandbox, and that directly gives access to the `Executor` interface. Instead it should give access to the `Workspace` interface, where the Executor is an interface inside the workspace interface.

The reason why i think this is good is because logically, the workspace is everything that is the "other world", where "this world" is the host machine. The workspace interface sits between this world and the other world, providing all the capabilities to whoever needs, to work with both worlds, or maybe just manage "other world". What do you think?

Here is what I think the Workspace interface should offer, depending on the problem and the feature we have described so far.

### Syncing things between host and the sandbox.

There are multiple layers to this, but it's responsibility is to provide ways the sandbox can be synced with the host. There are two ways data can move:
- Changes in the host can be brought into sandbox.
- Changes in the sandbox can be brought back into the host.

I am not ready to write the implementation strategy as of now, so we are just formulating and adding more details in iterations.

### Performance Optimizations:
When it comes to performance optimizations, there are many layers to the system, because we are trying to solve multiple problems.

#### Fast Boot
The biggest advantage of a MicroVM based sandbox is that they can start in milliseconds. But that startup time is not really relevant if the harness takes minutes to get it actually ready with all the code and work that is actually needed to work on the code. Copy times are the largest cost to the speed, now on top of that, imagine that same work for each sandbox to have ever started.

#### Dependencies
The second biggest problem any coding project faces is large dependencies needed to build the project, we cannot depend on the agent installing dependencies again and again, we want a way that installing dependencies is done as less times as possible and incremental if possible.

To tackle both these problems, we have come up with a versioned disk image management system, which are calling **prebuilds**.
